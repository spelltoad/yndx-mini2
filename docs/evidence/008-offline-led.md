## E18 — provenance и инструменты

На ПК создано изолированное `.venv`: pyelftools 0.32, capstone 5.0.6. Адреса ниже — **ELF virtual addresses**, не абсолютные runtime-адреса при ASLR.

## E19 — обработчик кнопки

Диапазон по ARM.exidx: **0x00c6e980–0x00c6ee90**. В пределах диапазона диагностический код ссылается на строки:

- `buttons_actions.cpp` — VA 0x002d5645;
- `handlePlayPause` — VA 0x00362247;
- `Toggle play/pause`;
- `Play/pause animation blocked by battery`.

Это сильная статическая идентификация функции, но не экспортированный symbol/debug info. Код проверяет условия, может переключать воспроизведение и отдельно пропускать анимацию. В частности, ветвь на 0x00c6eb8e ведёт к блоку выбора эффекта; альтернативная ветвь содержит сообщение о блокировке анимации батареей. Точное значение полей/модельная актуальность этой проверки не восстановлены: строки общего бинарника не доказывают наличие батареи в Мини 2.

Блок выбора:

```text
00c6ed2e  add r0, sp, #0x140
00c6ed30  cbz r5, 0x00c6ed42
00c6ed32  ldr r1, [pc, #0x154]
00c6ed34  add r1, pc                  ; -> "player_pause"
00c6ed36  bl  0x0067b1e0
00c6ed3a  mov r1, r4
00c6ed3c  bl  0x00c76e6a
00c6ed40  b   0x00c6ed50
00c6ed42  ldr r1, [pc, #0x148]
00c6ed44  add r1, pc                  ; -> "player_continue"
00c6ed46  bl  0x0067b1e0
00c6ed4a  mov r1, r4
00c6ed4c  bl  0x00c76e6a
```

Проверка ссылок независимо от эвристического сканера:

| LDR VA | Literal pool VA | ADD VA | Вычисленный target | Проверенные байты |
|---|---|---|---|---|
| 0x00c6ed32 | 0x00c6ee88 | 0x00c6ed34 | 0x002d494b | player_pause + NUL |
| 0x00c6ed42 | 0x00c6ee8c | 0x00c6ed44 | 0x002f391d | player_continue + NUL |

Thumb LDR pool = align(PC+4,4)+offset; target = literal + ADD_VA + 4 modulo 2^32. Обе проверки прошли assert. r5 получен ранее в функции; его точная высокоуровневая семантика не восстановлена, поэтому псевдокод не называет его isPlaying.

## E20 — helper и граница вывода

Общий helper **0x00c76e6a** сохраняет аргумент с выбранной строкой, получает два объекта через указатели в исходном объекте, затем:

- передаёт выбранный строковый объект виртуальному вызову (vtable +8);
- использует полученный результат в следующем виртуальном вызове (vtable +0x0c).

Это согласуется с lookup pattern → render/play. **Типы виртуальных объектов и финальное открытие файлов в этом проходе не восстановлены**, поэтому нельзя выдавать это за полностью доказанную цепочку до sysfs.

## Что теперь подтверждено

`observed (static)`: код кнопочного обработчика handlePlayPause выбирает **именно идентификаторы player_pause/player_continue** и передаёт их одному downstream-helper. Это сильнее E17, где были только строки.

`inferred, high confidence`: фиолетовые реакции touch play/pause, описанные владельцем, обслуживаются этой парой media-паттернов; они реально существуют в oknix и по содержимому согласуются с наблюдением.

`unknown`: точный путь физического input → handler, загрузчик ID → конкретный файл в текущем состоянии, кэш/hot reload, полный набор других callers и поведение после изменения. Поэтому до визуального runtime-эксперимента нельзя объявить физическое mapping окончательно проверенным.

## Инженерное следствие

Для будущей темы появились **обоснованные target assets: player_pause.led и player_continue.led**, а не alice_pro_* и не три rainbow-файла. Но изменение этих assets может затронуть других callers, найденных статическим поиском; touch-only изоляция не гарантируется. Перед записью нужен внешний бэкап обоих текущих файлов: ранее найденный RGB-бэкап содержит только alice_* и **не является бэкапом файлов player_***.

Никакой записи, перезапуска, input monitoring или визуального теста не было. Это результат статического исследования, не разрешение применять тему.
