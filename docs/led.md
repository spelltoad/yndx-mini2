# LED: установленная радуга и замена реакций

Статус: исследование, **не инструкция к немедленной модификации**. Основания: [E08 — радуга](evidence/003-modifications.md), [E11–E13 — LED и entrypoints](evidence/005-led.md).

## 1. Что установлено сейчас

«Rainbow» на этом экземпляре — **не плагин YAM и не фоновая программа**. Установщик `install-rgb-alice-mini2.sh` подменил три файла:

```text
/system/vendor/quasar/ledpatterns/oknix/alice_listening.led
/system/vendor/quasar/ledpatterns/oknix/alice_thinking.led
/system/vendor/quasar/ledpatterns/oknix/alice_speaking.led
```

Их SHA-256 совпадает с payload установщика. Имеются копии `/data/quasar/alice_rainbow_*.led` и сохранённые предыдущие файлы в `/data/quasar/rgb-alice-backup-<timestamp>-<pid>` (точное имя сохранено только в игнорируемом private/device.local.md).

Механизм: штатный quasar продолжает выбирать состояния/анимации; изменены данные трёх паттернов. Установщик после записи вызывает q restart; это **не доказывает**, что hot reload невозможен, и не разрешает повторять перезапуск автоматически.

Изменение этих трёх файлов не означает перекраску всех реакций: прочие `.led` и возможная программная индикация остаются отдельными механизмами.

## 2. Железо и формат

Локально есть 6 RGB-зон кольца, 18 LED-узлов sysfs, max_brightness 255 для каждого. В текущем `/sys/class/leds` нет clock-узлов. Каталог clock-паттернов в firmware есть — наличие ресурса не означает наличие железа.

В прочитанных кадрах Мини 2 — **шесть цветов RRGGBB + длительность**. Пример первого кадра установленной радуги:

```text
loop
FF1744 FF8A00 FFE600 20E060 00D9FF 744DFF 20
```

Upstream трактует последний столбец как миллисекунды; семантика директив loop/gammacorrection описана в wiki. Соответствие колонки конкретной физической зоне, гамма-функция и полная грамматика парсера на этом этапе не проверены. Не использовать трёхзонный пример Лайт как готовый паттерн Мини 2.

## 3. Фиолетовая реакция на центр панели

**Уточнения владельца (E14, E16):** касание центра не вызывает Алису — оно переключает play/pause ранее включённой музыки; короткая фиолетовая вспышка возникает **в обоих направлениях**. Голосовой вызов включает радугу, а запуск воспроизведения голосом **не даёт фиолетовой вспышки**. Исследуем **play/resume feedback**, а не listening. Первоначальная формулировка «центр / вызов Алисы» была неточной. Нужна точная цепочка:

```text
жест → событие/команда → состояние quasar → выбор паттерна/рендерера → LED
```

После уточнения и офлайн-анализа обоснованные target assets — **`player_continue.led` и `player_pause.led`**. В коде `buttons_actions.cpp / handlePlayPause` найден прямой выбор их идентификаторов (E19). Для `player_continue.led`: 10 кадров, пурпурный старт `e800f3` на всех шести зонах, плавное затухание, 800 мс суммарно по upstream-семантике тайминга. Литерал player_continue найден в maind. Это согласуется с наблюдением; связь **кнопочного handler → pattern IDs подтверждена статически**, но полный физический input → открытие файла → LED runtime-путь ещё не доказан. Подробности и полный файл: [E14–E15](evidence/006-playback-led.md).

Последний кадр player_continue не чёрный; погасание после завершения нельзя объяснить только содержимым файла без проверки рендерера. player_pause — отдельный похожий эффект 440 мс, заканчивается чёрным кадром. Фиолетовые alice_pro_* и intonation_spotting теперь не приоритетные кандидаты: нужное событие — воспроизведение, не диалог. Не приписывать смысл префиксу pro по догадке.

Rainbow меняет диалоговые состояния; кнопочный play/pause имеет отдельный выбор media-pattern ID, подтверждённый офлайн-дизассемблированием. См. [E18–E20](evidence/008-offline-led.md). Предыдущий этап [E16–E17](evidence/007-led-routing.md) содержал только строковые косвенные признаки. Выбор зависит от состояния и ограничений: код умеет пропускать анимацию; все условия ещё не восстановлены. Программный эффект или иной путь рендеринга пока не исключены. Важная граница scope: замена player_continue, если гипотеза подтвердится, может изменить resume-feedback **для всех источников управления**, а не только касания.

Нельзя менять все фиолетовые файлы «на всякий случай»: затронутся нецелевые реакции и исчезнет возможность понять причинную связь.

## 4. Два принципиально разных подхода

| Подход | Назначение | Ограничение |
|---|---|---|
| Точечная замена штатного паттерна | Изменить внешний вид конкретного уже существующего состояния, сохранив event routing | Нужен доказанный mapping; файл на rootfs, внешний бэкап и rollback обязательны |
| Runtime LED-модуль YAM/другой контроллер | Новые режимы/эффекты, связанные с пользовательским сервисом | Нужны событие, приоритеты, отмена и возврат управления; возможен конфликт с quasar |

**Предпочтение исследования** для запроса владельца — сначала точечная замена данных, если нужная реакция действительно паттерн. Это не утверждённый способ установки. Если реакция программная, понадобится другой адаптер.

В YAM v0.1.18 документированы `alice.set`, `alice.off`, `alice.play` с permission led. Это не свидетельство автоматического override конкретной реакции quasar. `off()` также нельзя без проверки реализации трактовать как «освободить кольцо».

Input-подписка не включается сама от permission led: отдельно нужны permission input и exact kernel-name allowlist. Для нашего экземпляра наблюдено `sar0_pad0`, но код и смысл события центра ещё не установлены. Подмена голосового диалога через `CANCEL_DIALOG` не нужна для обычной перекраски и не должна добавляться в LED-модуль автоматически.

## 5. Безопасный контракт расширения

Предлагаемый профиль `led-theme`:

- устройство: Mini 2, 6 RGB-зон, без часов;
- логический target: не имя файла, а подтверждённое состояние;
- renderer adapter: native pattern **либо** runtime, не два конкурирующих владельца;
- assets: версия/хеш, шесть цветов на кадр, проверяемый timing;
- invariants: не затрагивать mute/error/аварийную индикацию и штатные функции Алисы;
- rollback: восстановление точного исходного файла/владения, а не просто запись нулей;
- approval: отдельно на запись, возможный restart и визуальные испытания.

Приоритет mute — проектное требование безопасности, а не доказанная гарантия нынешнего драйвера/YAM. Не копировать trigger-управление Plum (`led_ring_fb`) на Mini 2 без проверки.

## 6. Следующие доказательства

1. Наблюдение владельца уточнено: касание resume музыки, голосовой вызов — радуга. Далее уточнить желаемый scope: только touch или весь playback resume.
2. Offline-анализ разрешён и выполнен: код обработчика подтверждён, имена player_pause/player_continue проверены по двум независимым PC-relative вычислениям (E19). При необходимости продолжить до типов виртуального helper и выбора файла; runtime-подтверждение всё ещё требует отдельного решения.
3. Если статического анализа мало — отдельно согласовать ограниченное наблюдение события/диагностического вывода с минимизацией персональных данных. Сейчас оно не разрешено.
4. После установления mapping отдельно выбрать цвет/эффект, scope и подготовить change spec + внешний бэкап.

**Target assets теперь обоснованы статически**, но окончательная runtime-проверка и допустимый scope ещё открыты. Для будущего изменения нужны внешние копии **обоих player_* файлов**: старый RGB-бэкап сохраняет только alice_* и не покрывает эти targets. Никакие LED, input-события или конфиги устройства в рамках исследования не менялись.
